Started: 2026-08-12. Local phase 12 Aug, preview phase 13 Aug, outage test 28 Aug.

## Configuration under test

## Test-scenario deviations

- The `visibility` exclusion scenario is skipped: it is defined by the WhiteWind lexicon, and this spike uses a custom NSID that has no `visibility` field (noted per plan U5).

## Findings

- **The spike's record shape never references a blob**, so criterion 6 cannot be exercised by its own content. KTD5 puts a filename in the record and the image in dyad's storage, which is the correct design and also means the mirror path has no caller here. It was tested against a referenced blob from `app.bsky.actor.profile` instead. The mirror belongs to the member-posted-image future, not to essays.
- **An uploaded blob is not retrievable until a record references it.** `uploadBlob` returned a CID; `getBlob` on that CID returned 500 until a referenced blob was used instead. Worth knowing before anyone builds on the upload half.
- **`cmdMirror` calls `getBlob` on the entryway**, which 302s to the real PDS. It works because `fetch` follows redirects, and it would stop working for a repo whose PDS the entryway does not know. Resolve the PDS first, as `xrpc.ts` already does.

- The read path works unmodified against a real PDS. Handle → DID → PDS resolution, `listRecords`, and `getRecord` all returned as the unit tests model them, with no code changes needed between the mocked tests and live traffic.
- `rkey = slug` pays off as designed: `/newsletter/[slug]` is one `getRecord`, no listing scan.
- Deleting a record removes it from the archive immediately on the uncached path. Retraction under KV is untested and is the thing KTD4 warns about, since values persist without a TTL.
- `spike-atproto.mjs` has no `delete` command. The `measure` command writes a probe record under the slug it is given and leaves it behind, so pointing it at a real slug would overwrite that essay. The probe record written during this phase was removed by a direct `com.atproto.repo.deleteRecord` call.
- Criterion 8 is untestable as the tooling stands. The only publish path is a Node script taking a hand-written JSON file, which is not a tool the essay author has today.

- **The outage fallback is real, and it is the only thing standing between a PDS outage and a 500.** With nothing cached, `ContentUnavailableError` reaches the route unhandled and SvelteKit renders a 500 page. Its own doc comment says callers "can render an explicit empty state or return 503 rather than 404" — no caller does. A cold isolate hitting a cold key during an outage therefore serves 500, not 503, so crawlers read it as a site fault rather than a retry-later. Cheap to fix in U7; recorded here because the spike is what surfaced it.
- **The XRPC timeout branch is untested.** `fetchJson` sets `AbortSignal.timeout(10_000)` and no test asserts it, in unit tests or live. The 5xx branch is covered both ways; a hung PDS is the one upstream failure whose behaviour under workerd is still assumed rather than shown.
- **KV entries are written with no expiration**, confirmed directly against the local namespace: both `content:entries` and `content:entry:ownership` store `expiration NULL`. KTD4 holds as designed, and with it the corollary — retraction is explicit invalidation or nothing.

## Verdict

**Six pass, one is partial, one fails.** Criteria 1, 2, 3, 4, 5 and 7 hold with measurements recorded above. The technical case is made: the read path works against a live PDS, survives a cold start under `nodejs_compat`, publishes inside the latency bound, serves last-known-good through an outage, and sits two orders of magnitude inside the PDS rate limit, with no new runtime dependency.

Criterion 6 is partial. Every guard in the mirror path is verified — allowlist, magic bytes, the spoofed-type rejection — and only the Storage write itself is untested, for want of a service-role key. It is also, per the findings, a path with no caller among the essays: KTD5 puts a filename in the record and the image in dyad's storage, so the mirror belongs to the member-posted-image future rather than to this content type. A criterion written for a path the chosen record shape does not use is a criterion mis-specified, not a capability missing.

Criterion 8 fails, and it is not close. Every publish in this spike ran through `node scripts/spike-atproto.mjs publish <entry>.json`, a developer holding a hand-written JSON file. The criterion asks for a tool that exists today, and none does. This was the known-hard one from the outset, and the evidence has not moved it: no general-purpose atproto client writes `social.dyad.unfolding.entry`, because the NSID is dyad's own and nothing else knows the shape. Answering it means building an authoring surface, which is U7 work, not spike work.

KTD8 says any unmet criterion is a fail, so on its own terms the gate is not passed. What the spike actually establishes is narrower and more useful than a pass/fail: **the atproto read path is sound and the authoring path does not exist.** Those are separable, and U6 is where that separation gets decided — whether Branch A proceeds with an editor build costed into U7, or whether the authoring gap is itself the argument for a Branch B source that ships an editor with it. The comparison table already names this as Branch A's principal risk. The spike confirmed the risk rather than retiring it.

The 3-working-day time-box is set aside by founder decision (2026-08-28) and is not a factor in the verdict.
