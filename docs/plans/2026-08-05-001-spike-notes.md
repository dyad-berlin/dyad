## Test-scenario deviations

- The `visibility` exclusion scenario is skipped: it is defined by the WhiteWind lexicon, and this spike uses a custom NSID that has no `visibility` field (noted per plan U5).
- The published entries are the three real essays from `src/lib/content/unfolding.ts`, converted field-for-field, rather than the synthetic `spike-entry.example.json`. This makes the parity check below possible.

## Measurements

Publish-to-visible, uncached, `localhost:5175`, 10 cycles:
`0.4, 0.4, 0.4, 0.5, 0.5, 0.5, 0.5, 0.6, 0.6, 0.8` seconds — p95 **0.8 s** against a 300 s bound.

Rendering parity, module adapter vs atproto adapter, same commit, same three URLs:

| Page | Visible HTML |
|---|---|
| `/newsletter` | identical |
| `/newsletter/conversation-is-a-fundamental-technology` | identical |
| `/newsletter/ownership` | identical |

The only byte-level difference across all three is JSON key order inside the SvelteKit hydration payload on the `ownership` page: `recordToEntry` emits fields in `ENTRY_FIELDS` order, so `paragraphs` precedes `heroImage`, where the module literal has the reverse. No rendering effect. R6 holds for the pages tested.

## Findings

- The read path works unmodified against a real PDS. Handle → DID → PDS resolution, `listRecords`, and `getRecord` all returned as the unit tests model them, with no code changes needed between the mocked tests and live traffic.
- `rkey = slug` pays off as designed: `/newsletter/[slug]` is one `getRecord`, no listing scan.
- Deleting a record removes it from the archive immediately on the uncached path. Retraction under KV is untested and is the thing KTD4 warns about, since values persist without a TTL.
- `spike-atproto.mjs` has no `delete` command. The `measure` command writes a probe record under the slug it is given and leaves it behind, so pointing it at a real slug would overwrite that essay. The probe record written during this phase was removed by a direct `com.atproto.repo.deleteRecord` call.
- Criterion 8 is untestable as the tooling stands. The only publish path is a Node script taking a hand-written JSON file, which is not a tool the essay author has today.

## Verdict

**Not reached.** One criterion passes, one is partial, six were not run. The local phase establishes that the read path and the rendering contract hold against a live PDS; it says nothing about workerd, caching, outage behaviour, media mirroring, rate limits, or authoring.

What remains before a verdict is possible: bind `CONTENT_KV` on the Pages preview environment, set the source gate there, deploy a preview, then re-run criteria 1, 3, 4 (20 cycles, cached path), 5, 6, and 7. Criterion 8 needs an authoring path that exists for the essay author, which on current evidence means it will be answered by building one rather than by testing one.
